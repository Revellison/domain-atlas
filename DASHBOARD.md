# Еженедельный отчёт и Domain Atlas

Всё готово для загрузки в **публичный GitHub-репозиторий**. Страница работает без сборки. В комплекте уже есть JSON из текущего CSV: **2138 доменов, 3750 уникальных IPv4, 343 ASN**. У 1189 доменов несколько IP, 178 найдены через поддомены, 43 пока без IPv4.

## Сразу посмотреть

В корне проекта выполните:

```powershell
python -m http.server 8765 --bind 127.0.0.1 --directory site
```

Откройте <http://127.0.0.1:8765/>. Нужен HTTP-сервер: открытие `index.html` двойным кликом не позволит загрузить JSON через fetch.

Таблица и панель поиска используют тёмно-серую палитру. Тонкие линии отделяют строки и панель пагинации. Поиск работает по доменам, IPv4, диапазонам, ASN, операторам и фактически найденным поддоменам. Фильтры по оператору и типу записи можно применять одновременно. Счётчик показывает число результатов, «Сбросить» очищает условия. `/` переводит фокус в поиск, Escape очищает строку поиска.

По умолчанию на странице **25 записей**. Можно выбрать 50 или 100. В DOM создаётся только текущая страница, остальные записи остаются в памяти для поиска. При смене фильтра открывается первая страница. Нажмите на строку, чтобы увидеть все адреса и соответствующие им сети. С клавиатуры перейдите к кнопке раскрытия и нажмите Enter или пробел. Подробности добавляются в DOM при раскрытии и удаляются после сворачивания. При системной настройке уменьшения движения анимация отключается. Сайт оператора открывается в отдельной вкладке. Если у одного IP несколько ASN, они отображаются отдельно. Для доменов без IP раскрытая строка показывает причину.

Выбор хостера открывает список с полными названиями, поиском по имени и ASN и количеством доменов. В нём отображается не больше **20 вариантов за раз**, есть отдельные стрелки страниц. Клавиши ↑/↓ выбирают вариант, Enter применяет, Escape закрывает список. Фильтр учитывает также дополнительные сети домена, даже если основная группа другая.

Адаптивная версия рассчитана на ширину от **320 px**. До 1140 px в компактных строках видны домен, IP, ASN и оператор. Диапазоны и сайты доступны в подробностях. Поиск занимает отдельную строку, два фильтра стоят рядом. На экранах до 680 px список хостеров открывается поверх страницы и учитывает высоту экранной клавиатуры. В пагинации отображаются стрелки и счётчик страниц. Длинные домены и поддомены переносятся.

Домены сгруппированы по организации оператора, затем ASN и имени. Если у домена несколько операторов, он отображается один раз в группе первого оператора по алфавиту; остальные видны внутри строки. CDN обозначает наблюдаемую сеть: скрытый origin за Cloudflare не выдумывается.

## GitHub Actions

1. Загрузите содержимое архива в корень публичного репозитория, включая `.github/`.
2. Перед каждым запуском `fetch_domains.py` скачивает свежий список в `build/input/domains.csv`. Этот файл используется и при локальном запуске по инструкции в [README.md](README.md). [Источник списка](https://cheburcheck.ru/whitelist/domains.csv).
3. Откройте **Actions → Weekly domain inventory → Run workflow** для первого запуска. В настройках репозитория Actions должны быть разрешены, а политика организации должна позволять workflow право `contents: write` для создания Releases. Отдельный GitHub PAT не нужен: используется встроенный `GITHUB_TOKEN`.
4. После завершения в **Releases → Latest** появится вложение `domains.json`.

Расписание — **каждый понедельник в 03:17 UTC / 09:17 по Омску**. Есть и ручной запуск. Workflow должен лежать в default branch; GitHub может задерживать расписание. В публичных репозиториях GitHub может отключить расписание после 60 дней без активности — его потребуется включить снова. [Документация GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Сначала скачивается актуальный CSV по HTTPS: максимум три попытки, 45 секунд на попытку, общий предел 180 секунд. Проверяются размер, кодировка, формат, доменные имена и количество записей. Пустой ответ, HTML, повреждённый CSV и список короче 100 уникальных доменов останавливают запуск. Минимум можно изменить repository variable `MIN_DOMAIN_COUNT`. Подстановка прежнего списка при сбое не выполняется. В релиз также загружаются скачанный список и метаданные источника, а в JSON сохраняются URL, дата скачивания, SHA-256 и число доменов.

Затем каждый запуск заново проверяет обычный DNS для **всего свежего списка**. Поиск поддоменов включается только для доменов без IPv4. Таймауты, ограничения параллельности, Retry-After и кеш прежнего скрипта сохранены. SQLite-кеш переносится между запусками через Actions Cache; его отсутствие не мешает проверке. Для этапа поддоменов отведён час, всему job — 110 минут.

Опциональные ключи добавляются в **Settings → Secrets and variables → Actions → Secrets**:

- `CERTSPOTTER_API_KEY`, `SUBDOMAIN_CENTER_API_KEY`;
- `PDCP_API_KEY` либо `CHAOS_API_KEY`;
- `BUFFEROVER_API_KEY`, `NETLAS_API_KEY`, `CENSYS_PAT`;
- `PEERINGDB_API_KEY`.

Без ключей работают доступные анонимные источники, а источники с обязательной авторизацией пропускаются. Ключи используются только сканером и не попадают в публичный JSON или страницу. Ограничения сторонних сервисов всё равно могут привести к неполным проверкам; предупреждения отражаются на странице.

Перед публикацией запускаются тесты и проверяется JSON. Если IPv4 найден менее чем у 50% доменов либо не найден ни один ASN, публикация останавливается и прежний latest остаётся доступен. Порог можно изменить repository variable `MIN_RESOLVED_RATIO` от 0 до 1; значение `0` отключает эту проверку. Это базовая защита от массового сбоя, а не гарантия полноты каждого отдельного результата.

Релизы получают уникальные теги. Сначала создаётся черновик, затем загружается JSON и только после этого релиз публикуется как latest. Старые релизы сохраняются; при ошибке публикации может остаться черновик, который не влияет на страницу.

## GitHub Pages: сайт и еженедельное обновление

Репозиторий: <https://github.com/Revellison/domain-atlas>. Адрес сайта: <https://revellison.github.io/domain-atlas/>.

Workflow `Deploy GitHub Pages` скачивает `domains.json` из конкретного latest-релиза, проверяет его и публикует вместе со страницей. Браузер загружает ту же копию JSON с домена Pages; прямой браузерный запрос к GitHub Releases не нужен. Отдельный сервер или Cloudflare для этого варианта не требуется.

Первый релиз содержит текущий отчёт. После каждого успешного еженедельного сканирования workflow `Weekly domain inventory` создаёт новый релиз и вызывает деплой Pages. Изменения интерфейса в `site/` также запускают публикацию; при этом данные берутся из последнего релиза. Можно запустить `Deploy GitHub Pages` вручную из Actions.

В другом репозитории включите **Settings → Pages → Build and deployment → Source: GitHub Actions**, создайте первый релиз с вложением `domains.json` и запустите workflow. Папка `site/` сохраняет локальный демонстрационный режим; файл `config.js` для Pages создаётся автоматически в `build/pages/`, исходники не перезаписываются.

## Альтернатива: Cloudflare Worker с прямой загрузкой из Release

У вложений GitHub Releases нет подходящего CORS для прямого браузерного `fetch` с другого сайта. В комплекте есть маленький **Cloudflare Worker**: он отдаёт страницу и `/api/domains`, который загружает:

```text
https://github.com/OWNER/REPO/releases/latest/download/domains.json
```

Это [официальный адрес latest-вложения](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases). Worker не использует GitHub REST API и не требует ключей. Успешный JSON кешируется на edge на 10 минут; ошибочные ответы не кешируются. После нового релиза страница получает свежие данные без передеплоя, с задержкой кеша до примерно 10 минут.

1. В `worker/wrangler.toml` замените `OWNER/REPO` на имя своего **публичного** репозитория.
2. Установите Node.js 22 или новее и выполните из корня проекта:

```powershell
npx wrangler@4.151.1 login
npx wrangler@4.151.1 deploy --config worker/wrangler.toml
```

Откройте выданный Wrangler адрес `https://domain-atlas.…workers.dev`. Он отдаёт и страницу, и JSON-прокси на одном домене. Файлы `site/` загружаются через [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/binding/). Сборка проверена командой `deploy --dry-run`, без фактической публикации в аккаунт.

Если хотите разместить HTML на своём статическом хостинге, загрузите туда содержимое `site/`, а в `site/config.js` задайте:

```javascript
window.DOMAIN_CONFIG = {
  dataUrl: 'https://ВАШ-WORKER.workers.dev/api/domains',
  demoUrl: './data/domains.json',
};
```

Worker разрешает CORS для этого публичного JSON. Приватные репозитории в этой конфигурации не поддерживаются. Произвольные сторонние URL через прокси передавать нельзя: источник фиксирован в серверной настройке `REPOSITORY`.

Пока `REPOSITORY = "OWNER/REPO"`, Worker отдаёт вложенный снимок. Обычный статический сервер без `/api/domains` также открывает этот снимок. Источник и дата указаны над таблицей и в названии вкладки. После настройки реального репозитория сбой GitHub или отсутствие релиза показываются как ошибка в таблице. `?demo=1` позволяет открыть локальный снимок на настроенном сайте. Перезагрузка страницы перечитывает снимок. Новый DNS-скан запускает workflow.

## Конвертация CSV и формат

Текущий JSON создан из `domains_report.csv`, дополнен метаданными из соответствующего `domains_report.details.json` и сохранён в `site/data/domains.json`. Повторить:

```powershell
python build_payload.py domains_report.csv --details domains_report.details.json --output site/data/domains.json
```

Можно передать только CSV; тогда группировка использует имена операторов вместо идентификаторов организаций, а дата берётся из времени изменения CSV. Никакого повторного сетевого сканирования конвертация не запускает.

Корневые поля JSON: `schema_version`, `generated_at` (UTC), `summary`, `warnings`, `domains`. Один объект в `domains` — один исходный домен. В `addresses[]` находятся IPv4, в `networks[]` каждого адреса — диапазоны, ASN, имена операторов и сайты; `resolved_via[]` содержит фактически проверенные DNS-имена. `providers[]` перечисляет операторов домена, `group` задаёт основную группу. `resolution` принимает `direct`, `subdomain` либо `unresolved`. IPv6 конвертер отклоняет.

ASN здесь — BGP origin из Team Cymru; ссылка оператора берётся из PeeringDB. Это наблюдаемая маршрутизация, не юридическое доказательство владения диапазоном.
